## 三、为什么我漏了——方法论差异，不是运气

看完 Codex 的报告，差距原因很清楚：

| 维度 | Codex | 我 |
|---|---|---|
| **是否实际执行** | **是**。"以下包含 8 项已复现的源码问题"；R1 直接贴了 `./mitom --version` 的报错，R2 用 `/bin/false` 替换验证程序实测，R7 造了一条 2000 个 N 的 FASTA 真跑 `mitom annotate` | **否**。全程静态阅读 + 静态工具，**一次没运行过 `mitom` 命令** |
| 运行平台 | Linux（`/mnt/p/Mitom`），能复现 CRLF、权限、锁、超时等真实环境问题 | Windows，且只有 `python -m`，`./mitom` 这类入口根本没碰 |
| 审查取向 | 沿数据流走：输入 → 转换 → 注释 → 验证 → 输出，每步问"失败了会怎样" | 按模式扫描：异常吞没、原子写、并发、复杂度 |

**关键差距在 R1**：我在 Windows 上 git clone，`core.autocrlf` 把工作区转成 CRLF。我全程用 `python -m pyflakes`、`python -m ruff`，**从没执行过 `./mitom`**，所以完全没机会看到 `python3\r: No such file or directory`。这是环境选择直接导致的盲区——我在一个"问题不会显现"的环境里做审查。

**R2/R3/R4 同源**：都是"外部工具失败了，但失败没有被正确传播"。我查过 `subprocess.run` 的 `check` 参数（ruff PLW1510 报 10 处），但判断为"都走 `run_tool` 封装，误报"就停了。**我没有继续追问：`run_tool` 默认 `check=False`，调用方有没有检查返回值？** Codex 追了，追出了 3 个 P1。

这一点我要承认：**我把工具告警判为误报时，停止了深挖，而这个"误报"背后藏着真问题。**

## 五、我这次的教训（写给下次的自己）

1. **不实际运行，就没有资格称"审查"。** 静态工具能找模式，找不出"跑起来会怎样"。
2. **判"误报"之前必须追到底。** PLW1510 那 10 处我一句"走 run_tool 封装"就放过了，漏掉 3 个 P1。
3. **选错平台等于自断视野。** Windows + `python -m` 的组合，天然看不见 CRLF、权限、锁、shebang 这类问题。
4. **"工具没报" ≠ 没问题。** 死循环那条（`mito_nuc.py:387`）没有工具报出来，是我读出来的；反过来，Codex 的 6 个 P1 工具也基本没报。
