### 问题 1【中】计数失败静默跳过，仍提交输出，返回值可能是陈旧值

**位置**：`mitom_output.py` 第 288–297 行（函数 `finalize_genbank_output`）

```python
288        # ── Step 4: recount from definitive file ──────────────────────
289        try:
290            pcg, trna, rrna = counts_from_genbank(draft_gb)
291            # cox1_first from the file itself: a linear record is never rotated (rotate_record), whatever
292            # reorient_one_gb counted
293            orientation_ok = starts_with_gene(draft_gb, which_gene_first, force_forward)
294        except Exception:
295            pass
296        os.replace(str(draft_gb), str(dest_gb))
297        committed = True
```

**分析**：

- 第 177 行 `pcg = trna = rrna = 0`，第 178 行 `orientation_ok = False`，所以不会 NameError。
- 但 Step 1（第 191 行 `rewrite_genbank_record_ids`）已经给 `pcg, trna, rrna` 赋过一次值。**如果 Step 4 的 `counts_from_genbank` 抛异常，函数返回的是 Step 1 时的旧计数**，不是最终文件的实际计数。
- 更微妙的是：`counts_from_genbank` 与 `starts_with_gene` 在**同一个 try 块**内。若前者成功、后者失败，则 `pcg/trna/rrna` 已更新，而 `orientation_ok` 保持 Step 2（第 202 行）可能设成的 `True`。此时最终文件方向若有变化，返回值仍报 `True`。
- 第 296 行 `os.replace` 在 try/finally 之后照常执行，**即使 Step 4 完全失败，输出文件仍被提交，退出码不受影响**。
- 该函数返回值用于 pipeline 的 summary（第 307 行 `return pcg, trna, rrna, metadata_mode, orientation_ok`），下游据此写 `annotation-summary.tsv` 与统计。

**影响**：输出 GenBank 文件本身是 draft 的真实内容（文件已生成），但**报告里的基因计数和方向标记可能与该文件不符**，且无任何警告。

**为何算"中"**：不损坏序列数据，但损坏统计结果的可信度。对批量注释工具，计数是用户筛选结果的主要依据。

### 问题 2【中】部分失败返回退出码 0，自动化流程无法感知

**位置**：`mitom_pipeline.py` 第 854–857 行

```python
854        if total and len(summary.annotation_failed) == total:
855            logging.warning(f"[FAIL] every record failed in the annotation core ({total}): see reports/failed_logs/")
856            return 1
857        return 0
```

同样的判定也出现在第 443 行（`if samples and len(summary.annotation_failed) == len(samples)`）。

**分析**：只有**全部记录都失败**才返回 1。100 条记录中 99 条失败、1 条成功，退出码仍是 0。

**另有一处更值得注意**：`curated.ok`、`submitted.ok`、`compared.ok`、`maps.ok` 通过 `steps.done(..., ok=...)` 只用于界面显示（第 810、814、839、843 行），**不参与退出码判定**。也就是说，**NCBI 校对步骤（table2asn）失败、基因组图生成失败，退出码依然为 0**。

**为何算"中"**：批量工具返回 0 表示"跑完了"，这里实际语义是"至少有一条跑完了"。用于 `mitom run ... && 下游脚本` 或 CI 时，部分失败会被静默放过。

**需要说明**：失败样本确实写入了 `reports/annotation_failed.txt`、`reports/all_problem_samples.txt`（第 416–417、793–794、781 行），**有留痕**。所以这是"设计取舍"而非疏漏——但对不了解该约定的使用者是陷阱。README/CHANGELOG 里是否有明确说明，我未逐字核对。

### 问题 3【中】元数据替换直接覆盖输出文件，非原子写

**位置**：`mitom_metadata.py` 第 336–339 行（函数 `transfer_gb_metadata_file`）

```python
336        replaced_text, stats = replace_metadata_in_text(
337            new_text, exact_dict, clean_dict, norm_dict, smart=smart, auto_accept=auto_accept)
338        output_gb.parent.mkdir(parents=True, exist_ok=True)
339        output_gb.write_text(replaced_text, encoding="utf-8")
```

**分析**：`Path.write_text` 直接截断并写入目标文件，不是"临时文件 + `os.replace`"。

- 写到一半失败（磁盘满、进程被杀、断电）→ 留下**半个 GenBank 文件**，且原内容已丢失。
- 若调用方传入 `output_gb` 与 `new_body_gb` 相同（原地改写），**源数据不可恢复**。
- 对比：`mitom_output.py` 采用了 `draft_gb` + `os.replace` 的原子写法（第 182、296 行），**同一项目内两种写法不一致**。

**影响**：单文件损坏，不扩散。GenBank 记录本身是文本，用户可能有备份，故列"中"不列"高"。

**我未确认的风险点**：调用方是否可能传相同路径，我没有追完所有 `transfer_gb_metadata_file` 的调用链。这一点需作者确认。

### 问题 4【中低】文件分片循环存在理论死循环

**位置**：`mito_nuc.py` 第 384–390 行（函数 `blast_db`）

```python
384        for p, a, b in zip(parts, cuts, cuts[1:]):
385            f.seek(a)
386            with open(f"{p}.fa", "wb") as o:
387                while a < b:
388                    chunk = f.read(min(b - a, 1 << 24))
389                    o.write(chunk)
390                    a += len(chunk)
```

**分析**：若 `a < b` 但 `f.read()` 返回空（`b""`），则 `len(chunk) == 0`，`a` 不递增，**`while a < b` 永不退出**。

触发条件：`b` 超过文件实际可读长度（文件在 `f.stat().st_size` 与读取之间被截断/替换），或 SEEK 位置越过文件尾。

`size` 来自第 365 行 `fa.stat().st_size`，`cuts.append(size)` 在第 383 行。正常情况下 `a < b ≤ size` 且文件不变，不会触发。**属于防御性缺陷，不是常见路径 bug。**

补充：第 391 行 `parts = parts[:len(cuts) - 1]`，`n >= 2` 时 `cuts` 至少为 `[0, size]`，长度 2，切片安全。

### 问题 6【低】格式探测的宽泛 except 会掩盖真实错误

**位置**：`mitom_inputs.py` 第 191–199 行

```python
191        try:
192            ...
196                        break
197        except Exception:
198            pass
199        return "fasta"
```

**分析**：探测文件是 FASTA 还是 GenBank 时，任何异常（权限、路径、IO）都被吞掉，**默认返回 `"fasta"`**。若真实原因是"文件无权限读"，后续会被当成 FASTA 解析并报出与根因无关的错误，**误导排查方向**。

**注**：`mitom_inputs.py` 第 302 行那处 except 是本报告初筛时误判，实际有 `logging.warning` 记录，无问题。

## 四、一个悬而未决的技术问题（非缺陷，需作者判断）

**`ORIGIN_EXT = 3000` 对内含子是否会不够？**

- `mito_core.py` 用 3000 nt 附加副本处理跨原点的蛋白基因，对动物线粒体基因（最长 ND5 约 1.7 kb）**足够**。
- 但本项目专门做内含子注释（`mito_intron.py` 1,631 行，`mito_intron_ref.py` 2,040 行）。部分类群（如刺胞动物、部分软体动物的 *cox1* 内含子）**单个内含子可超过 3 kb**。
- 我查看了 `mito_intron.py` 与 `mito_intron_ref.py` 中 `ORIGIN_EXT` 的使用，**未出现该常量**——说明内含子注释走的是另一套坐标逻辑。但我**没有完整读完这两个文件（共 3,671 行）**，无法断言跨原点长内含子已被正确处理。

**这条不是指控，是我能力边界内的未完成检查。** 建议作者自行确认：一个跨原点、总长 > 3 kb 的含内含子基因，`mitom` 是否能完整注释。

## 七、结论

**代码质量高于同类学术软件的平均水平。**

具体表现：统一的外部程序调用封装（`run_tool`）、可选步骤的失败隔离（`optional_step`）、主流程输出原子写入、无 bare except、无 assert 逻辑、29 个模块全部带详细 docstring 且注释标注了来源日期、41 个测试文件配 benchmark 脚本。

**发现的问题集中在三类**：

1. **失败路径的可见性**（问题 1、2、6）—— 出问题时静默跳过，调用方与用户难以察觉
2. **原子写入不一致**（问题 3）—— 同一项目内两种写法
3. **防御性不足**（问题 4、5、8）—— 正常输入不触发，异常输入可能死循环或崩溃

**没有发现**：算法层面的明显错误、坐标系处理错误、遗传密码表映射错误、并发的数据竞态。

考虑到作者已在 git 提交中记录过多轮 fuzzing 和模块自审，这个结果与预期一致。
