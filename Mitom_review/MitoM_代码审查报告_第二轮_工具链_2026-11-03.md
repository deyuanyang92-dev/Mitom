## 一、本轮确认为**真实问题**的发现

### 新发现 A【中】`tarfile.extractall` 在项目目标 Python 版本下无过滤保护

**位置**：`mito_env.py` 第 361–362 行

```python
361        with tarfile.open(tgz) as tf:
362            tf.extractall(target, **({"filter": "data"} if hasattr(tarfile, "data_filter") else {}))
```

**bandit 报 B202（HIGH）**：`tarfile.extractall used without any validation`。

**我的核实结论——这条是真的，但风险被三层因素压低**：

1. 作者**已经写了** `filter="data"` 的保护，这是正确的修法。
2. 但**项目目标环境是 Python 3.11**（`env/mitotools.yml`: `python=3.11`），而 `tarfile.data_filter` 是 **Python 3.12 才引入**。`hasattr(tarfile, "data_filter")` 在 3.11 返回 `False`，**代码会走空字典分支，等于没有任何过滤**。
3. 我在本机（Python 3.13）验证：`hasattr(tarfile,'data_filter')` → `True`。**所以这个降级路径在开发机上测不出来，只在目标环境触发。**

**为什么风险仍然低**：
- 下载源是硬编码的 Zenodo URL（`REF_URL` 常量），非用户输入
- 第 357 行有 **MD5 校验**，与官方 `REF_MD5` 不匹配就删除并退出
- 内容既已通过 MD5 校验，tar 内部结构的可信度较高

**残余风险**：若 Zenodo 记录被替换且 MD5 同步更新（或被中间人同时篡改），cwd 之外的任意路径可被写入。概率极低但路径确实存在。

**一个可验证的推论**：如果把环境降到 Python 3.11 跑 `mitom setup`，自定义 `filter` 不会生效；用 3.12+ 才会。建议作者在 3.11 环境下加手动成员检查，或显式要求 3.12+。

### 新发现 B【中低】下载的模型文件未校验文件名，存在路径穿越可能

**位置**：`mito_intron.py` 第 556–560 行

```python
556            with urllib.request.urlopen(SUBTYPE_CM_URL, timeout=30) as r:
557                items = json.load(r)
558            for it in items:
559                if it["name"].endswith(".cm"):
560                    urllib.request.urlretrieve(it["download_url"], SUBTYPE_CM_DIR / it["name"])
```

**问题**：两个字段都直接来自 GitHub API 的 JSON 响应，**都没有校验**：

1. `it["download_url"]` —— 未校验 host。正常应是 `raw.githubusercontent.com`，但代码不检查。若 API 响应被篡改，可指向任意地址。
2. **`it["name"]` 直接拼进保存路径** —— 若值为 `../../x.cm` 或 `C:/Windows/x.cm` 这类，`SUBTYPE_CM_DIR / it["name"]` 会**写到缓存目录之外**。这是典型的 CWE-22 路径穿越。

**为什么是「中低」不是「高」**：
- URL 是 https，且源是 GitHub 官方 API + 一个有 DOI 的公开学术仓库（Selles Vidal et al. 2025）
- 第 561 行 `except Exception` 会把失败降级为"只用 Rfam 模型"，不会中断
- 触发需要攻击者控制 GitHub API 响应或该仓库内容，前提较强

**但这是代码层面的实际缺口**：`it["name"]` 应做 `Path(name).name` 去路径化 + 白名单后缀校验。bandit 的 B310 只报了 scheme 问题，**没报这一层**，是我读代码发现的。

## 二、被工具报出、但我核实为**误报**的（重要，避免误导作者）

这一节同样重要。如果不加区分，作者会被噪音淹没。

### 误报 1：B023「闭包捕获循环变量」45 处 —— 绝大多数安全

这是 ruff 报得最吓人的一类（`function-uses-loop-variable`），理论上是并发/延迟调用场景的经典 bug。逐点核查结果：

| 位置 | 情况 | 判定 |
|---|---|---|
| `mito_intron.py:817-824`（**24 条，最集中**） | `shifts()` 在循环内定义，**同一次迭代内立即调用**（第 825 行） | **安全**：闭包取到的是当前值，不是循环结束值 |
| `mito_core.py:615, 617, 622` | `spliced_join` 已用 `ref: str = ref` 显式绑定默认参数 | **安全**：这正是 B023 推荐的修法，作者已做对 |
| `mito_nuc.py:1983-1991` | `inside()` / `dovetail()` 定义后在同段内 `filter(dovetail, hsps)` 立即使用，`pieces` 期间不变 | **安全** |
| `mito_compare.py:257-258` | 同为立即调用 | **安全** |

**结论**：B023 在此项目中基本是规则本身的局限（它对"循环内定义、循环内调用"也会报）。**没有发现真正的延迟调用 bug。**

### 误报 2：B905「zip 未指定 strict」60 处 —— 多数不能加

Python 3.10+ 的 `zip(strict=True)` 会在两序列不等长时报错。看似是好建议，但：

| 位置 | 代码 | 为什么不能加 strict |
|---|---|---|
| `mito_intron.py:667` | `zip(blocks, blocks[1:])` | **故意错位配对**，长度天然差 1。加 strict 必崩 |
| `mito_curate.py:992` | `zip(fn, kn)` | 前一行已限定 `abs(len(fn)-len(kn)) <= 3`，用 `0.95*max(len)` 作分母，**本就为不等长设计**。加 strict 必崩 |
| `mito_intron.py:666` | `zip(aln.aligned[0], aln.aligned[1])` | Biopython 同一比对的两行，长度必然相等，安全 |
| `mito_intron_ref.py:581` | `zip(qseq, sseq)` | BLAST outfmt6 的 qseq/sseq 同长度，安全 |

**结论**：B905 是这批工具里**误报率最高**的规则。批量加 `strict=True` 会直接引入崩溃。

### 误报 3：vulture `mtime` 未使用 —— 是 lru_cache 的缓存键

`mitom_stage.py:68`：

```python
@functools.lru_cache(maxsize=64)
def _file_lineages(path: str, mtime: float = 0.0) -> Dict[str, str]:
```

`mtime` 函数体内确实不用，但它是**缓存失效的键**（文件改动时间变了 → 缓存 key 变 → 重读）。**这是正确设计**，删掉它缓存就永不失效。

### 误报 4：B324「weak MD5」 —— 用于完整性校验，用途正当

`mito_env.py:357`（校验 Zenodo 下载）、`mitom_inputs.py:332`（序列哈希）。

两处都**不是安全用途**（不用于密码、签名、身份验证），是内容完整性/去重。bandit 会一律报 HIGH。建议的规范化写法是加 `usedforsecurity=False`（Python 3.9+）以表明意图，但**当前用法本身没有安全缺陷**。

### 误报 5：`mitom_inputs.py:370` 的 `None` 解引用（mypy union-attr）

mypy 报 `Item "None" of "GbRecordMeta | None" has no attribute "version_int"`。

**核实**：`by_acc: Dict[str, GbRecordMeta]`，第 350 行 `prev = by_acc.get(key)` → 类型为 `GbRecordMeta | None`。第 367 行 `if key not in by_acc: ... else:` —— 进入 else 说明 key 必在字典中，**`prev` 逻辑上一定不是 None**。

**结论**：运行时安全。这是 mypy 无法跨分支收窄类型导致的，属**类型标注可改进**，非 bug。
