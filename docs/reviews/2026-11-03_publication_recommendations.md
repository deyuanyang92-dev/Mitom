# MitoM 正式发表与软件发布建议

日期：2026-11-03。依据：本地 `655a75c`、现有方法与评测资料，以及本轮[代码审查记录](2026-11-03_codex_release_review.md)。本文件只记录建议，没有修改代码、既有结论或发布状态，也没有执行投稿、上传或正式发布。

这里将“正式发表”理解为发表 MitoM 软件／方法论文，同时准备可供读者使用的正式软件版本。建议与期刊要求分开标注；样本量、图表数量等建议值不是期刊硬性门槛。

## 1. 总体判断与论文定位

MitoM 已有形成方法论文的材料：原生注释核心、学习的起点与 tRNA 判别、跨原点处理、内含子识别与位点迁移，以及跨类群评测。当前最需要投入的是证据独立性、比较公平性和可复现发布。

建议把论文集中在“动物线粒体注释的基因边界、复杂结构与结果可追溯性”。从这几个方面选出一项主贡献和两项主要支持，明确每项贡献相对已有工具新增了什么。对 MITOS2／MiTFi、MFannot、Infernal 等继承的方法、模型与代码分别归因。

可供验证的研究问题是：在未参与训练和规则调整的动物谱系上，MitoM 能否改善基因检测和边界定位，同时保持可接受的假阳性、运行成本和流程完成率？目前的文档结果可用于设计研究，最终论文结论需与冻结版本及独立评测绑定。

`mitom nuc` 的核 rDNA／组蛋白功能建议暂放补充材料或作为后续工作；若纳入主贡献，需要独立的真值、比较方法和误差分析，论文范围会明显扩大。

优先顺序：**修复正确性问题 → 冻结版本与数据划分 → 独立评测与生物学核实 → 归档和外部试用 → 写作投稿**。本轮仍只记录这些待办，不实施修复。

## 3. 最优先补齐：独立测试与参考泄漏审计

### 3.1 每条记录都需要可追踪的数据身份

建议建立统一的数据清单，至少包括 accession.version、taxid、谱系、序列校验值、数据获取日期，以及属于训练／开发／最终测试中的哪一部分。RefSeq 与 GenBank 镜像、不同 accession 的相同序列、旋转或反向互补的相同环状序列，应归入同一划分单元。

同时记录各条序列是否进入了：参考蛋白、分类参考、tRNA 分支协方差模型、tRNA 判别／端点训练、P11 起点训练、rRNA 模型，以及内含子位点库。只排除目标 accession，不足以证明所有模型和参考都没有见过同种或同一序列。

已有按科划分和留一结果值得保留；下一步应把分散记录汇成一份可由脚本检查的清单。这里提出的是证据核对需求，尚未证明现有全部结果存在泄漏。

### 3.2 P11 的训练关系必须特别交代

当前 `models/start_model/start_model.json` 元数据列出 1,683 条训练记录，训练集合含 `mito_bench_annelida_2026-10.tsv` 与 `mito_bench_large_2026-10.tsv`。训练脚本确实先按科交叉验证，再拟合全量模型。

因此，使用这个全量模型重新运行上述集合得到的结果，应按实际重叠情况标注；不能直接当作独立泛化表现。按科交叉验证产生的折外预测可以支持交叉验证结论，但还需要确认上游特征生成、规则选择和参考排除没有使用测试折标签。

### 3.3 保留两种有不同用途的评测

| 评测条件 | 回答的问题 | 报告方式 |
|---|---|---|
| 正常随附参考库 | 读者实际安装后通常能得到怎样的结果 | 明确目标与近缘记录是否在库内 |
| 留种／留属／留科，或独立时间留出 | 对参考较远或开发期间未见的数据能否泛化 | 公布所有受影响的参考和模型排除规则 |

建议在当前开发结果之外，再冻结一批从未用于规则选择的测试记录，按主要类群、遗传密码和困难结构分层。所需规模取决于主要指标的不确定性；无需为了总数漂亮而大量增加近缘样本。测试集看过后据此改规则，应将其转为开发数据，并另保留最终检验。

## 4. 比较要能区分算法改进与后处理收益

主比较建议至少覆盖 MITOS2 和 MitoZ；内含子方法主张需与 MFannot 或适当的内含子方法比较；tRNA 贡献需保留真正 MiTFi 的对照。仓库已有六工具试验和校正前后比较，可整理为统一协议。每项对照应选投稿时能够稳定运行的版本，公开版本号、完整命令和参数。

建议分别展示三类结果：

1. **原生输出**：各工具按明确的推荐设置处理相同裸序列，用来比较实际使用效果。
2. **统一后处理**：适用工具的结果经过同一版本 MitoM 校正，量化校正模块本身的收益。
3. **完整流程**：最终交付结果，包括拓扑、重注释、内含子和格式处理，用来评价用户实际获得的产物。

比较时记录双方可用的分类信息、遗传密码、参考数据、线程数、内存和超时。MitoM 若读取 GenBank 分类与密码，而对照只获得裸 FASTA，应另设信息相同的比较。修改过的 MITOS2 fast 包装器与未经修改的 MITOS2 应明确区分。

所有工具都成功的 `common_ok` 子集可用于配对定位精度；同时必须报告全部尝试记录上的完成率、超时率和失败类型，避免只统计成功记录造成偏差。相同输入遇到不支持的类群时，应记录支持边界。

## 5. 指标、统计与真值应分层报告

### 5.1 基因检测与边界定位分别统计

| 方面 | 建议主要指标 | 必须说明的定义 |
|---|---|---|
| PCG | 召回、精确率、起点准确率、终点准确率、两端一致率 | 分母是全部真值基因还是已匹配基因；部分基因如何处理 |
| tRNA | 召回、精确率、每基因组假阳性、链／反密码子／边界正确率 | 一对一匹配规则；重复拷贝；Leu／Ser 编号归一化 |
| rRNA | 检出率、边界偏差分布、两端一致率 | 参考端点的证据级别；边界不确定的处理 |
| 内含子 | 检出与剪接位点准确率、阴性假阳性 | 与原始 NCBI、纠正金标准分别比较；分参考排除等级 |
| 完整流程 | 有效输入中最终完成比例、验证完成比例、资源消耗 | 所有尝试记录的分母；可选步骤失败和主流程失败 |

使用一对一的位点匹配，防止一个预测同时算作多个真值命中。环状坐标、跨原点 join、部分端点和同名拷贝需要统一规则。保留原始基因名；用于评分的名称映射应公开，尤其避免将 MITOS2 与 NCBI 的 Leu／Ser 编号约定差异直接计为生物学错注。

同时给出总体微平均与按类群的宏平均，以及样本数，防止大门类主导结论。一个门只有一至数条记录时，可以报告观察结果，不宜据此声称该门普遍更优。

建议报告同一记录上的配对差值及置信区间。重采样至少以基因组为单位；同属／同科高度相关时考虑按分类簇重采样，并说明方法。不要把同一基因组内的许多基因当作完全独立的重复。

### 5.2 NCBI 注释的一致性与生物学正确性应分别解释

PCG／rRNA 的“与 NCBI 两端完全一致”是重要的比较指标，但参考注释本身存在错误或不同约定。若模型也以 NCBI 起点为训练目标，论文应明确其学习目标。

内含子金标准已有 97 个位置与 NCBI 不同，且位点库来自这些已核实记录。因此，全库 309/309 主要支持已收录位点的处理能力；留一 299/309 和留属等结果更适合支持泛化讨论。对证据不足或只能部分核实的类别，应单独给出结果。

建议对各方法之间的分歧、共同失败和 MitoM 特有预测进行盲法核查。可先以约 30–50 个代表性分歧位点规划工作量，再按问题扩充；这不是正式样本量要求。核查者先按预定标准判断证据，再揭示工具身份。

若已有独立 RNA-seq、跨剪接位点 reads 或原始组装 reads，可用于关键新内含子、端点或拓扑主张。没有这些证据时，保留“计算预测／证据不足”的边界，避免将工具间一致当作独立实验证实。

## 6. 做能解释贡献的消融与困难案例

建议先做以下有明确问题的消融，避免堆积大量无目的组合：

| 比较 | 要回答的问题 |
|---|---|
| P11 开／关，使用折外或独立记录 | 起点学习的收益是否稳定，哪些类群会退步？ |
| MitoM-ML、MiTFi、生产组合策略 | 提升来自判别器、补漏还是二次确认？ |
| 从头内含子、仅位点迁移、两者结合 | 已知位点迁移与新位点识别各贡献多少？ |
| 拓扑自动判断／显式正确标签，第二轮开／关 | 复杂端点处理能否纠错，会不会错误拼接或裁剪？ |
| 校正前／后 | 修正和新引入的错误分别有多少，净收益是多少？ |

困难案例至少包括：真实线性序列与末端重复、跨原点基因／内含子、少 tRNA 类群、重复 tRNA、不同遗传密码、片段／高 N 序列、远缘谱系和失败的外部程序。转录组装片段、嵌合或异常输入若超出支持范围，也要给出可理解的失败或不确定状态。

## 7. “可提交 NCBI”需要重新建立完整证据

代码审查已确认验证非零退出、超时和 FATAL／REJECT 汇总存在问题。不能据此认定历史 2,497 条记录全部有错；也不能继续只以当前 `ncbi_errors=0` 列证明它们都已通过验证。

建议修复后由独立于 MitoM 汇总逻辑的检查脚本，对冻结最终结果重新运行指定版本的真实 table2asn，保存：

- 每条记录的执行命令、退出状态、开始／结束时间及 stdout／stderr。
- 本次产生的提交产物与验证报告；排除残留旧文件。是否应产生 `.val` 等文件按该版本和参数核实，不能把文件缺失直接解释成通过。
- 全部严重级别消息，并分别统计“验证未完成”“验证完成且有阻断消息”“验证完成且无阻断消息”。
- 输入、产物与工具的版本或校验值，以及每一类有意保留的警告。

论文和 README 可以据此准确表述“生成提交材料，并在指定验证版本下完成检查”。最终接收还涉及提交者信息及 NCBI 审核，不应承诺自动获得接收。

## 8. 可复现的软件版本与许可说明

### 8.1 从论文数字回到可执行材料

建议归档一份明确版本的发布候选，包含代码提交、模型、参考快照、划分清单、命令、逐记录结果和生成论文图表的脚本。每个主要数字都应能追到原始表、评分代码、运行版本和样本分母。

将临时目录、其他机器的绝对路径、未收录的 `mitom_work/` 数据整理为可获取的数据包或可验证重建说明。仅有重新查询 NCBI 的脚本不能保证未来获得相同记录版本；保留 accession.version、获取日期、校验值，并在允许的条件下归档实际快照。

性能评测公开硬件、线程／并发数、wall time、CPU time、峰值内存、下载量和磁盘占用；区分首次训练／解压／建库与缓存后运行。

正式分发物至少在干净 Linux 环境、容器和一个读者可复制的安装路径上验收。当前本地没有 `.github/` 目录，尚未核实是否另有外部 CI；建议建立或公开自动检查，覆盖安装、核心测试、少量真实工具集成、只读安装目录配合可写缓存，以及失败退出行为。CRLF 修复应在实际归档包和容器构建上下文中核验。

邀请 2–3 位未参与开发的使用者按英文说明独立安装、运行示例并报告阻塞，是有价值的实用检验；这是建议人数。保留支持渠道、版本变更和贡献说明。

Bioinformatics 当前明确要求软件文章提供可用实现、测试数据和文档，并将提交的软件版本与测试数据归档到专门仓库；数据可用性声明也应明确。因此 GitHub 开发地址之外，应准备带持久标识的归档版本。[Bioinformatics 官方作者指南](https://academic.oup.com/bioinformatics/pages/author-guidelines)

### 8.2 先厘清现有许可表述

本地可直接核实：根 `LICENSE`、`CITATION.cff` 及 README 对本仓库代码作 CC0 总体表述；`mito_intron.py` 文件头明确声明该文件按 GPL-3.0 分发；`models/mfannot_proteins/LICENSE.md` 为 GPL-3.0；MiTFi 另有 MIT 许可。

建议建立逐组件来源与许可清单，明确自有代码、移植代码、随附模型／数据和仅调用的外部程序各自的条款，并统一 README、CITATION、包元数据及发布包的表述。现有总体表述不能让读者误以为 GPL 文件也被统一改成 CC0。涉及组合分发的具体许可结论，应在完整核查后确定；本文件没有替作者更改许可证或认定违法。

若考虑 JOSS，尤其要核对其 OSI 许可要求：其审查标准要求 OSI 批准的许可证，而 CC0 官方 FAQ 说明 CC0 未获 OSI 批准。不能仅凭根目录已有 CC0 就认定符合该投稿门槛。[JOSS 审查标准](https://joss.readthedocs.io/en/latest/review_criteria.html)、[Creative Commons CC0 FAQ](https://wiki.creativecommons.org/wiki/CC0_FAQ)

## 9. 论文结构与图表建议

建议先确定主张，再将现有材料放入以下证据结构；具体数量随文章类型压缩：

1. **方法与贡献图**：输入到最终结果的流程，标出继承组件与 MitoM 新增部分。
2. **主评测图**：独立数据上的配对精度、类群差异和全部输入完成率；主要分母直接可见。
3. **机制／消融图**：起点、tRNA 组合、内含子或拓扑处理中最能解释主贡献的一组实验。
4. **复杂案例与资源图**：代表性分歧的证据、失败边界与运行成本；短文可部分移到补充材料。

主文聚焦需要读者相信的结论；逐记录表、所有参数、完整类群分层、完整错误清单及运行日志归档到补充数据。结果部分主动呈现 rRNA 边界不确定、远缘类群和低置信度预测，讨论这些局限如何约束使用。

写作前统一术语：

| 用语 | 建议固定含义 |
|---|---|
| MitoM | 整个软件与完整流程 |
| MitoM-ML | tRNA 学习模块，不等同于包含 MiTFi 等步骤的全部生产策略 |
| NCBI 一致率 | 与指定参考注释的吻合程度 |
| 生物学正确性 | 由明确证据标准支持的注释正确程度 |
| 验证通过 | 指定验证工具与参数下确认完成且无所定义的阻断消息 |

## 10. 期刊路线：按证据与文章体量选择

以下匹配判断是建议，不代表录用概率。政策于 2026-11-03 查询；确定目标后应再次核对文章类型、格式、费用和声明要求。

| 路线 | 对 MitoM 的适配判断 | 投稿前重点 |
|---|---|---|
| **Bioinformatics，Application Note 或 Original Paper** | 若能清楚展示独立的方法贡献和公平评测，可优先考虑；短文需高度聚焦 | 安装可用、独立证据、归档版本；复杂模块过多时考虑完整方法文章 |
| **Bioinformatics Advances** | 可作为软件／方法文章的另一候选；官方列有原创研究与 application notes | 按最终文章体量和主贡献选择类型，核对详细指南 |
| **NAR Genomics and Bioinformatics** | 若保留较完整的跨类群评测、复杂结构与可复现材料，可考虑 | 官方要求在投稿时提供支撑结果的数据访问，软件可用且能运行 |

## 11. 可执行的准备顺序与验收依据

| 顺序 | 工作 | 完成依据 |
|---|---|---|
| 1，正式发布前 | 处理审查 R1–R9，明确失败状态与输出完整性 | 各复现转为回归测试；在正式分发物上确认，原始输入不被静默破坏 |
| 2，最终评测前 | 冻结版本、参考、模型与数据身份 | 可校验清单；训练／开发／测试及各模型接触关系明确 |
| 3，投稿前 | 独立完整流程评测与公平对照 | 逐记录结果、全部尝试分母、分层和配对统计可复算 |
| 4，投稿前 | 核实关键分歧与 NCBI 验证状态 | 证据分级表、独立验证日志；无依据的强结论被收窄 |
| 5，投稿前 | 完成贡献消融、困难案例及资源测量 | 能解释增益来源和退步条件 |
| 6，公开分发前 | 统一许可与来源声明 | 组件清单及 README／CITATION／包内许可表述一致 |
| 7，投稿前 | 外部试用、英文文档、版本和数据归档 | 陌生使用者可复现示例；论文关键数字可由归档材料重建 |
| 8，投稿时 | 按目标期刊准备正文和声明 | 作者确认全部事实，提交材料无未决占位符 |

建议以完成这些证据为进度判断，不预先承诺几周内能发表。当前优先补正确性和独立性；新增界面、更多可选引擎等功能可按主贡献需要安排。
